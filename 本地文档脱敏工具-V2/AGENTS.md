# 本地文档脱敏工具 V2 协作规则

## 1. 产品边界

- 产品必须是 Windows 10/11 x64 本地桌面应用，最终通过便携包或 EXE 交付。
- 断网时仍应完成读取、识别、复核、脱敏、复查、映射和报告生成。
- 不提供上传入口、云端处理、API 调用、遥测、CDN、远程字体或自动更新。
- 原文件只读，不覆盖、不移动、不静默改名。
- 只能生成 AI 分析副本，不宣称完成保密审查、解除密级或保证可外发。

## 2. 目录保护

- `../本地文档脱敏工具/**` 是旧版程序保护区，V2 不得修改。
- `../本地文档脱敏工具-UX原型/**` 是原型参考区，V2 不得反向修改。
- V2 只允许修改 `src/**`、`ui/**`、`tests/**`、`docs/**`、`harness/**`、`scripts/**`、`AGENTS.md`、`DESIGN.md`、`README.md`、`pyproject.toml` 和打包配置。
- 不得把真实用户文件、原文、词库、映射表、任务输出或密码提交到仓库。

## 3. 权威顺序

1. 当前用户确认。
2. `docs/prototype/02-DECISIONS.md`。
3. 需求、字段、状态和验收矩阵。
4. `DESIGN.md`。
5. UX 原型的视觉与交互实现。
6. 旧版已验证的处理能力。

### UX 原型强制对齐

- `../本地文档脱敏工具-UX原型` 是 V2 界面唯一设计源，不是风格参考或灵感来源。
- V2 必须逐项对齐原型的布局、侧栏宽度、间距、颜色、字体层级、文案、组件结构、按钮位置、状态反馈、返回路径和交互顺序。
- 不得自行增加、删除、合并或重新解释原型中的界面功能；原型中已确认的操作必须在正式应用中保留。
- 若旧版引擎能力与原型交互不一致，应增加适配层，不得为了迁就旧 UI 改变原型基线。
- 任何无法完全对齐的地方必须记录在 `02-DECISIONS.md`，经过用户确认后才能实施；不得由开发者自行取舍。

发现范围、核心字段、状态或交付方式变化时，必须先更新矩阵和 harness，暂停源码修改。

## 4. 技术边界

- 优先复用旧版 Python 处理引擎和测试；新建独立 UI/状态桥接层。
- 首选 PySide6/QML 原生桌面壳，禁止把 Vite 页面直接当作正式交付程序。
- 先完成单文件 DOCX 最小闭环，再迁移规则库、历史、XLSX、文件夹队列和图片/OCR。
- 每个阶段只实现一个可验证闭环，不做并行视觉探索。
- 界面实现完成前，必须用原型页面和状态逐屏对照；截图只用于核对，不得替代交互验收。

## 5. 安全与输出

- AI 交付目录只放脱敏分析副本。
- 本地保管目录放脱敏映射表和检查报告，并持续显示“严禁上传”。
- 明文原值只允许存在于内存和本地映射表，不进入日志、报告、历史摘要或 AI 交付目录。
- 映射表当前不设置密码输入，但不得因此弱化本地保管和严禁上传警示。
- 旧格式、宏、加密/IRM、损坏或无法安全拆解的 OOXML 必须阻断，不得降级处理。

## 6. 验证门槛

- 先通过静态 harness，再通过单文件真实测试闭环和旧版回归测试。
- 第 4 步进入、生成失败重试、返回上一步、输出目录隔离必须有可复现证据。
- 不以“端口可访问”、旧截图或模拟 toast 代替功能证据。
- 本地完成、EXE 打包、外部发布是三个独立授权，不得自动发布。
