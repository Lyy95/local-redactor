# 本地文档脱敏工具 AI 协作规则

本文件是 AI 参与本项目分析、设计、开发和验收时的首要入口。修改任何产品源码前，必须先完整阅读本文件。

## 一、依据优先级

出现冲突时，按以下顺序执行：

1. 用户在当前任务中的最新明确结论。
2. 本文件“用户明确需求”章节。
3. `docs/prototype/02-DECISIONS.md` 中仍然有效的决策。
4. `docs/prototype/01-REQUIREMENTS.md`、`03-FIELD_MATRIX.md`、`04-STATE_MATRIX.md`。
5. `DESIGN.md`。
6. 当前可运行程序。
7. 仅作为风格参考的截图、参考项目和历史备份。
8. AI 自行推断。

不得静默采用已经被替换的旧规则。无法判断的冲突必须记录到决策文档的待确认区，并向用户说明。

## 二、用户明确需求（长期有效）

### 1. 使用背景与安全目标

- 用户需要借助 AI 阅读和分析资料，但原始资料可能涉密，不能直接上传外部 AI。
- 工具必须在本机离线完成读取、识别、脱敏、复核、映射和导出，不提供任何上传入口。
- 工具只生成供 AI 阅读的分析副本，不改变文件密级，也不替代单位的保密审查和外发审批。
- 所有由用户确认属于涉密、敏感或必须隐藏的内容，都必须改成代号、星号形式或删除，不能保留完整原文。

### 2. 首版文件范围与交付形式

- 首版至少支持现代 Word `.docx` 和 Excel `.xlsx`。
- 旧版 Office、宏文件、加密文件、损坏文件和危险 OOXML 文件必须阻断，不能降级处理。
- 最终交付必须是可以在 Windows 10/11 x64 上直接使用的便携版程序，包括 ZIP、EXE 和中文使用说明。
- 每次任务生成：同格式 `AI分析副本`、本地 HTML 技术检查报告、可直接打开的本地 XLSX 脱敏映射表；映射表只能位于 `本地保管`，严禁上传。
- `AI交付` 只允许包含分析副本；映射表和检查报告只能放在 `本地保管`。

### 3. 必须覆盖的识别内容

- 个人身份：姓名、身份证号、手机号、地址、车牌、账号。
- 组织业务：单位、部门、项目、系统名称。
- 场景信息：地点、金额、案件编号、设备编号；时间类当前不自动识别、不自动替换，原文保留。
- 网络信息：IP、域名、内网地址、邮箱、用户名。
- 图片内容：图片文字、印章、签名、二维码、照片和人脸候选。
- 文件内部信息：文件属性、作者、修订记录、批注、隐藏文字。
- 文档结构和对象：页眉页脚、水印、附件、嵌入对象、超链接、隐藏工作表、隐藏行列。
- 组合风险：多个普通字段组合后能够识别特定人员、单位、事件或内部目标的情况。

### 4. 脱敏结果必须可读

- 不能把所有内容统一替换成无意义的 `XXX`，脱敏后仍要看得懂角色、关系、事件顺序和数量级。
- 同一实体在正文、表格、不同工作表和图片 OCR 中必须使用同一个代号。
- 优先使用一致代号、适当模糊、范围表达和保持结构的虚构值。
- 用户自定义的 `GA`、`WJ`、`jz`、`qb` 等代号必须原样使用，程序不能擅自解释或扩写。
- 用户当前约定警种和公安部门优先使用大写拼音首字母代号；出现撞码时改用正式全称的首字母组合，确保不同警种可区分。
- 类似 `530网` 的内容可按用户规则转换为 `5**网`。

### 5. 界面与操作体验

- 界面必须简洁、优雅、低密度，避免大段常驻说明和晦涩术语。
- 固定四步流程：`选文件 → 自动检查 → 确认处理 → 生成文件`。
- 第三步必须让普通用户立即知道如何操作，主要动作使用：`采用建议`、`修改`、`保留原文`、`删除`。
- 必须提供 `采用全部普通建议`，但不得批量处理图片、低置信度未知内容、组合风险、附件和未知对象。
- 每次操作必须立即反馈、更新剩余数量并进入下一项；失败不能无响应。
- 主界面不得出现“一致别名、结构模拟、降低精度、区间化、统一平移、比例变换、像素处理、转为可见附注、确认并应用策略”等内部术语。

### 6. 本机规则库与判断标准

- 用户可以长期沉淀固定替换，例如 `公安 → GA`、`网警 → WJ`。
- 用户可以新增判断标准，保存命中条件、处理方式、是否必须替换、正确示例和反例。
- 支持界面新增、编辑、启用、停用、删除，并支持 CSV/XLSX 导入和空白模板导出。
- 规则不能只在本次输入中生效；关闭程序、重新打开后仍须存在。
- 规则库使用 Windows 当前用户级加密保存，不能进入项目目录、任务输出、日志、HTML 报告或 AI 分析副本。
- 导入内容与现有规则冲突时，必须让用户选择 `保留现有规则`、`采用导入规则` 或 `取消导入`，不得静默覆盖。
- 点击 `以后都这样处理` 后要保存为长期规则，并在当前已解析文字与 OCR 缓存上增量应用。
- 增量应用后刷新当前任务规则快照；保留无冲突的已完成决定，不重读文件、不重跑 OCR。

### 7. 强制规则和最终防漏

- 命中强制规则后，`保留原文` 必须不可用，只能使用代号、星号形式或删除。
- 规则创建、应用、人工修改和最终导出都必须检查：替换结果不能通过大小写变化、插入符号或增加后缀继续保留完整原词。
- 局部规则命中不能删除更大范围的普通敏感候选，未覆盖部分必须继续复核。
- 组合风险及其贡献字段不能被一键操作间接关闭，必须由用户单独确认。
- 最终必须重新打开实际生成的文件，对可见文字、OOXML 部件、媒体 OCR、二维码、原图片字节、外链和活动对象进行独立复扫。

### 8. 脱敏映射表

- 每次完成任务都必须生成一张本地 XLSX 脱敏映射表，方便用户后续对应核对；最新用户结论取消密码输入。
- 映射表至少包含：映射编号、内容类别、原始值、脱敏值、处理方式、出现次数、位置、规则来源和还原说明。
- 明文原值只能出现在内存和 `本地保管/脱敏映射表.xlsx` 中，不能生成其他明文中间映射文件；密码、密钥和令牌不得写入映射表。
- 映射表必须与 `AI交付` 严格分目录，并持续标记“严禁上传”。

### 9. 第三轮确认范围

- Word 副本必须保留原文件的页面、分节、样式、编号、文字格式、表格和图片锨点；只改变经确认的内容和必须清理的安全对象。
- 规则库的“判断标准”必须预置常用个人信息、凭据、网络和业务对象标准，并可编辑、停用和删除。
- 固定替换和判断标准预置只写入本机加密规则库一次；用户删除后不得在下次启动自动补回。
- 处理中修改规则时，必须在已解析文字和 OCR 缓存上增量应用，保留无冲突的已完成决定，不自动从头扫描。
- 首页支持单文件和文件夹队列；文件夹默认当前层，可选包含子文件夹，且单个文件失败不得伪装成成功或阻断后续项。
- 历史处理记录使用 Windows 当前用户级加密，可保存文件名、哈希、本机路径、时间、状态、数量和结果路径，不保存原文或可逆映射。
- 图片只将人脸、结构化敏感信息和强制规则命中列为待处理；普通 OCR 文字、普通照片和颜色块不进入待办。

## 三、两阶段工作方式

### 分析阶段

- 检查需求、现有代码、截图、导航、数据和真实行为。
- 完成模块说明、需求覆盖、字段矩阵、状态矩阵、设计基线、验收场景和机器契约。
- 未经用户确认，不修改产品源码。
- 将需要确认的内容合并成一次确认，避免反复打扰用户。

### 实施阶段

- 只有用户确认基线后才能开始。
- 已确认范围发生变化时，先同步需求和矩阵，再修改源码。
- 只实现已确认的最小闭环，保留未被点名删除的功能、字段、入口和交互。
- 简单修改只改直接命中项，不扩展到无关模块。
- 修改可维护源码，不直接修改生成产物；最终交付必须由当前源码重新构建。

## 四、关键项目文件

- `DESIGN.md`：视觉和交互规则。
- `docs/prototype/00-MODULE_BRIEF.md`：模块范围与保护面。
- `docs/prototype/01-REQUIREMENTS.md`：需求覆盖。
- `docs/prototype/02-DECISIONS.md`：有效、已替换和待确认决策。
- `docs/prototype/03-FIELD_MATRIX.md`：跨页面字段一致性。
- `docs/prototype/04-STATE_MATRIX.md`：状态、操作和流转规则。
- `docs/prototype/05-ACCEPTANCE.md`：自动化与人工验收计划。
- `docs/prototype/06-UX_AND_RULE_LIBRARY_REVISION.md`：极简界面和规则库确认基线。
- `harness/prototype-contract.json`：命令、路径、文案、安全约束和验收旅程。
- `harness/progress.md`：当前进度、证据、已知限制和交付信息。

## 五、不可突破的安全边界

- 原文件只读，禁止覆盖、重命名、移动或静默复制。
- 禁止云 API、联网请求、遥测、崩溃上传、自动更新、远程字体、CDN 和 AI 平台直传。
- 禁止在日志中记录原文、命中值、完整路径、密码和可逆映射。
- 图片脱敏必须真正改写像素并重新编码，不能使用可移除的视觉遮罩。
- Word 输出必须在原 OOXML 版式结构的安全副本上改写，保留页面、分节、样式、编号、表格和图片锚点，并移除未允许的 OOXML 部件。
- 公式不得执行；外链、宏、ActiveX、OLE 和未解决嵌入对象不得进入分析副本。
- 仓库和测试只能使用虚构、脱敏数据，禁止提交真实用户文件、词库、映射表和任务输出。
- 不得使用“已解密、已脱密、可安全上传、绝对安全、100%安全”等保证性文案。

## 六、验收要求

完成前必须：

1. 执行构建、类型检查、代码检查、静态检查和完整自动化测试。
2. 执行 `harness/prototype-contract.json` 中配置的关键旅程。
3. 验证新闭环和所有受保护流程。
4. 检查界面、控制台和生成文件中的错误与敏感信息。
5. 执行独立工程和安全审查，解决全部 P0/P1。
6. 运行打包后 EXE 自检，并校验 ZIP 的 CRC、文件数量和目录一致性。
7. 将最终证据记录到 `harness/progress.md`。

任何必需检查失败时，不得宣称完成。

## 七、发布边界

- 本项目交付本地 Windows 便携程序，不进行网站部署。
- 实施确认、最终打包和外部部署是不同授权，不得相互替代。
- 未经用户明确授权，不得上传、发布或向外部系统发送任何项目产物。
